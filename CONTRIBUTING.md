# Contributing

Раздел описывает работу над библиотекой: настройку окружения, проверки, документацию, ветки и оформление pull request. Выпуск и публикация версий описаны отдельно в [Releasing](https://gocream-labs.github.io/pysberbank/next/releasing/).

Общий порядок работы:

1. Создайте рабочую ветку от актуальной `next`.
2. Внесите небольшое, законченное изменение и добавьте тесты для изменённого поведения.
3. Запустите подходящие локальные проверки.
4. Оформите коммиты в формате gitmoji со скоупом.
5. Отправьте pull request в `next` и дождитесь CI и review.


## Local Setup

Окружения управляются через [Hatch](https://hatch.pypa.io/). Зависимости каждого окружения перечислены в `pyproject.toml` и устанавливаются при первом запуске соответствующей команды.

Для тестов и основного dev-окружения используется Python 3.10, для линтера, документации и релизных инструментов - Python 3.14. Матрица тестов охватывает Python 3.10-3.14.

Из корня репозитория выполните:

```sh
hatch run init
```

Команда подключает `.git-blame-ignore-revs` к `git blame` и устанавливает pre-commit и commit-msg хуки. При изменении файлов библиотеки или `pyproject.toml` pre-commit запускает Ruff; gitlint проверяет форму заголовка коммита. Проверка форматирования и тесты запускаются отдельно. Команда `hatch run remove` отменяет локальную настройку хуков и `git blame`.


## Checks

| Command | Purpose |
|---|---|
| `hatch run test:check` | Тесты с покрытием на Python 3.10 |
| `hatch run mtest:check` | Матрица Python 3.10-3.14 и отчёт `coverage.xml` |
| `hatch run compatibility:check` | Python 3.10 и Requests 2.28.2 для совместимости с потребителем |
| `hatch run lint:check` | Статический анализ Ruff |
| `hatch run lint:fmt-check` | Проверка форматирования без изменения файлов |
| `hatch run lint:format` | Автоисправление Ruff и форматирование |
| `hatch build --clean` | Чистая сборка sdist и wheel |
| `hatch run package:check` | Строгая проверка метаданных готовых дистрибутивов через Twine |

Начинайте с тестов изменённого компонента, затем запускайте затронутый набор. Например, для подготовки параметров запроса:

```sh
hatch run test:check tests/request_data.py -q
```

Тестам запрещены сетевые обращения через `pytest-socket`. HTTP-ответы подменяйте моками; реальные платежи и обращения к внешним сервисам в тестах не выполняются. Регрессионный тест должен воспроизводить исправляемую ошибку и проверять результат, а для сериализации - фактически переданные HTTP-параметры.

Для небольшого изменения ограничивайте автоформатирование конкретными файлами:

```sh
hatch run lint:format tests/request_data.py
```

`package:check` проверяет содержимое `dist/`, поэтому сначала выполните `hatch build --clean`. Старые ошибки тестов и линтера исправляйте отдельными осмысленными изменениями, не отключая проверки ради зелёного CI.


## Documentation

Документация собирается через MkDocs Material. Навигация описана в `docs/SUMMARY.md`, справочник API генерируется из docstring с помощью mkdocstrings.

| Command | Purpose |
|---|---|
| `hatch run docs:build` | Строгая сборка сайта в `site/` |
| `hatch run docs:links` | Проверка внутренних ссылок уже собранного сайта |
| `hatch run docs:serve` | Локальный сервер с обновлением при изменении исходников |
| `hatch run docs:versions` | Список опубликованных версий документации |
| `hatch run docs:links-external` | Отдельная сетевая проверка опубликованного сайта и внешних ссылок |

После изменения навигации, ссылок или API-справочника запускайте `docs:build`, затем `docs:links`. Публикация версий сайта выполняется релизными workflows; её порядок описан в [Releasing](https://gocream-labs.github.io/pysberbank/next/releasing/#documentation).

Главная страница включает `README.md`. Страницы Roadmap, Changelog и Contributing - относительные символические ссылки на корневые `ROADMAP.md`, `CHANGELOG.md` и `CONTRIBUTING.md`. Редактируйте исходный файл, сохраняя ссылки: так сайт и репозиторий используют один текст, а дата изменения берётся из Git-истории исходника.

Заголовки страниц и названия разделов меню пишутся на английском, основной текст - на русском. Сведения о методах и их параметрах храните в docstring, а страницы справочника используйте для группировки методов и перекрёстных ссылок.


## Docstrings

Новые и существенно изменённые docstring пишутся на русском в [Google-style](https://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings). Они должны объяснять контракт: значение параметров, формат результата, ограничения и возможные ошибки.

Используйте секции `Args:`, `Returns:`, `Raises:`, `Yields:` и `Examples:` по необходимости. Атрибуты класса описывайте в `Attributes:`, параметры конструктора - в docstring `__init__`. Типы не нужно повторять, если они уже указаны в аннотациях.

Например, описание результата метода статуса можно оформить так:

```python
"""Возвращает статус заказа по идентификатору платёжного шлюза.

Args:
    orderId: Идентификатор заказа, полученный при регистрации.

Returns:
    Исходный словарь ответа API.
"""
```

Ссылки на документированные объекты оформляйте с полным путём: `[SberbankClient][gocream_pysberbank.http.SberbankClient]` или `[BaseSberbankException][gocream_pysberbank.errors.BaseSberbankException]`. Это позволяет mkdocstrings связывать страницы справочника без ручного указания URL.

Старые docstring приводятся к Google-style постепенно, поэтому предупреждения их парсера пока отключены через `docstring_options.warnings: false`. Это не отменяет строгую проверку сборки и ссылок.


## Branches

В релизной схеме используются две долгоживущие ветки:

- `next` - разработка, RC-релизы и документация `next`;
- `master` - стабильные релизы.

После создания `next` в удалённом репозитории рабочую ветку можно подготовить так:

```sh
git fetch origin
git switch next
git pull --ff-only
git switch -c codex/request-parameters
```

Выбирайте короткое имя, описывающее изменение. Обычные изменения возвращаются в `next` через PR. Beta можно вручную выпустить из рабочей ветки до merge; PR в `master` готовит stable-релиз, предварительные beta и RC для него необязательны.

После stable-релиза синхронизируйте `master` обратно в `next`, чтобы release-коммит и тег вошли в историю дальнейшей разработки.


## Commits

Заголовок состоит из emoji-маркера [gitmoji](https://gitmoji.dev/), скоупа и краткого описания на английском:

```text
🐛 (client): Preserve zero request parameters
🔇 (client): Remove sensitive request logging
✨ (client): Add API method
🎨 (style): Format code
```

Скоуп обозначает затронутую область, например `client`, `tests`, `docs` или `project`. При необходимости в теле коммита поясните причину изменения и последствия для совместимости.

`💥` повышает major, `✨` - minor; поддерживаемые исправления и конфигурационные изменения повышают patch. `🎨`, `🧪` и `📄` попадают в changelog без повышения версии. Полные списки находятся в `[tool.semantic_release.commit_parser_options]` в `pyproject.toml`.

Gitlint проверяет форму заголовка, а релизное значение маркера определяет Python Semantic Release. При squash merge итоговое сообщение тоже должно соответствовать этому формату. Добавление нового маркера описано в [Releasing](https://gocream-labs.github.io/pysberbank/next/releasing/#versioning).

Версию и `CHANGELOG.md` вручную не меняйте. Changelog формируется из коммитов при выпуске, а не отдельным коммитом в каждом PR. Ожидаемую версию можно посмотреть без записи файлов и публикации:

```sh
hatch run release:preview
hatch run release:beta-preview
```


## Pull Requests

Перед отправкой PR:

1. Добавьте или обновите тесты изменённого поведения.
2. Запустите подходящие проверки из [Checks](#checks), а при изменении структуры документации и ссылок - из [Documentation](#documentation).
3. Просмотрите diff и выполните `git diff --check`; уберите случайные и не относящиеся к задаче изменения.
4. Опишите проблему, итоговое поведение и выполненные проверки.
5. Отдельно отметьте изменения публичных сигнатур, исключений, формата ответов или совместимости с потребителями.

CI проверяет поддерживаемые версии Python, совместимость с Requests 2.28.2, упаковку, код и документацию. Если обнаружена существующая ошибка вне задачи, укажите её отдельно, не ослабляя тесты и проверки. После успешного CI изменения должны пройти review.

Не смешивайте исправления платёжного клиента, массовое форматирование и настройку публикации в одном изменении. Для релизного PR в `master` дополнительно следуйте [Releasing](https://gocream-labs.github.io/pysberbank/next/releasing/).
